# Doc Sum qualification permits and enrollment

**Draft for a design decision.** The Linux deliverable is an offline harness that can run the Doc Sum candidate through the verified client and return a receipt. It must be possible to qualify a candidate before it has earned production enrollment. This annex proposes the authority and interface for steps 2 and 4 of the [U1b delivery sequence](PR-Shared-Runtime-U1b-Consumer-Approval.md#required-change-surface-and-sequence). Juan owns acceptance at an exact revision. Live allowances, enrollment of a release, hardware policy and implementation require their own decisions.

## Who may authorize what

**Juan would issue approvals as release operator. The model client would admit them.** The application supplies the reviewed program and checker. The host supplies a lease and reports the instance. Oversight reviews the evidence. An application, a peer, a reviewer verdict or a successful run cannot issue authority.

Use an offline Ed25519 release signature over a versioned record with a purpose-specific signing prefix and the exact payload bytes. Assign a dedicated runtime-qualification verification key to the official client build. One operator can approve both purposes, with a distinct signed purpose and a distinct closed payload type for each. The trusted key identity comes from the frozen client package. Without a provisioned trusted public key the real entry cannot admit a permit. A record, adjacent key file, environment setting or test fixture cannot supply or replace it. Reuse the existing release pattern for protected private-key custody and exact-byte verification. The proposed runtime key is separate from entitlement keys because possession of billing authority must not authorize model execution. There is no per-customer key, second approver or online signing service. Key creation, provisioning, rotation and signing are outside this proposal. Bind the selected public key into the client **before** freezing the candidate. A replacement build or trust anchor needs a new identity comparison.

### Signed bytes and API boundary

The proposed envelope contains only `format_version` (integer 1), `purpose` (`qualification-invocation` or `production-enrollment`), `key_id`, `payload_base64url` and `signature_base64url`. The decoder selects the expected purpose from its entry point, matches `key_id` to the package-pinned runtime public key, and requires canonical unpadded base64url. Verify the 64-byte Ed25519 signature over the ASCII prefix `local-connect/runtime/v1/`, the expected purpose in ASCII, one zero byte, and the decoded payload bytes in that order. Verify those bytes directly, without reserializing JSON. A relabeled envelope fails verification under the other prefix.

Each payload is a closed UTF-8 JSON object covering the bindings in its row above. Digests refer to exact retained bytes and use lowercase SHA-256 hex. The challenge is 32 random bytes from the runner's OS, encoded once as lowercase hex. Counters and ceilings are nonnegative integers with an explicit unit and range. Time allowances are monotonic durations. Any approved absolute validity window uses UTC and also constrains dispatch. Apply bounded strict decoding, including rejection of duplicates at every level, unknown fields, invalid lengths, overflows and fractional counters. Large manifests, programs and receipts are bound by digest and verified separately, so their contents need not travel in the envelope. Freeze byte-level fixtures and measured parser bounds with the executable schema increment. No operational limits are granted here.

The fixed candidate measures its local artifact set and loads its compiled program/checker binding. Admission compares those identities to the signed manifest and annex. The signed enrollment stays external to the frozen executable, libraries and assets. Signing it after qualification does not require rebuilding the executable to embed its own digest.

The proposed client API first prepares a pending invocation from the candidate’s fixed definition and offers its challenge. It then consumes that pending invocation with the authenticated permit to execute the bound plan and return evidence. Only an internal admitted invocation owns the wire capability. Both the normal ready-client entry and the qualification entry reside in the same candidate bytes that will be compared at release. Neither accepts a flag that turns the other into an unrestricted session.


## One invocation from approval to evidence

1. **Prepare locally.** The fixed client prepares a pending invocation in its originating process. It generates an unpredictable challenge internally, records the process identity and exact candidate/plan digests, and presents a reviewable request. Preparing cannot acquire a lease, start discovery, contact a peer, tokenize or generate. The nonce is public. The pending state is private, non-cloneable and non-serializable.
2. **Approve and claim once.** Juan authorizes that exact candidate, phase and budget in its numeric annex and signs the matching invocation. After checking purpose, key, challenge, bindings and process identity, the client atomically consumes the pending state before it opens the lease or performs a probe. Two concurrent claims have one winner. Another process, a forked child or a restart cannot import the pending state or choose the old challenge. Closing the runner before use invalidates it. The execution deadline starts on dispatch after admission, within any validity window explicitly approved by the annex. There is no mandatory short operator-response window.
3. **Bind the instance.** The admitted interface owns the lease throughout. Verify the registered host/server process identities, socket and runtime tuple with the existing attachment and transport owners. Bind the first verified instance when the approved invocation permits startup, or require the specified existing instance when the plan names one. Charge each permitted probe before issuing it. An identity change, reconnect or re-verification mismatch ends the invocation.
4. **Reserve and dispatch.** The harness supplies only the frozen input or the next operation from the signed transition program. The client accepts no free-form URL, program pointer, widened limit or replacement checker. A synchronous Doc Sum adapter may drive the approved program. The internal permit and verified session stay private. Return a terminal receipt with the raw decoded result or typed failure, usage and reservation history. Keep private output in the operator-owned evidence location. Never return a production `ReadyClient` from this entry.

The existing writer budget remains the owner of logical work selection. Extend its reserve-before-delegation semantics into a single invocation budget whose private send boundary enforces the signed ceiling. A logical reservation identifies the stage, ordinal and request/probe plan. Each underlying host start, identity probe, tokenizer send, generation and re-verification gets a linked reservation against its own operation class **before** its first possible side effect. These are separate units. A forwarded send is charged once, with one authoritative balance for its class. Callers can inspect receipts but cannot replenish the balance or substitute a permissive callback. Looking up existing preflight results or a cached production canary cannot satisfy an invocation that requires fresh evidence.

G1 authorizes only the enumerated startup, probe, observation and tokenizer work, with zero generation. G2 requires reviewed G0/G1 and its own signed numeric annex for the exact canary and stage generations. Include per-operation counts and bytes, input/output token allowances where applicable, phase and request deadlines, and aggregate ceilings. Dynamic input is admissible only through the bound transition code, validated predecessor and finite branch budget. A reserve that cannot be recorded prevents dispatch. Cancellation or a timeout after reservation retains the charge and terminates the run. A dropped connection after a possible send records delivery unknown. A crash leaves incomplete evidence and requires fresh operator authority to run again. Retain a protected local record of the candidate, instance, phase, transitions, offers, refusals, sends and outcome. Publish only bounded receipts and aliases. Exclude credentials, signed bearer material and private document or model content from shared evidence.

## What the offline proof must break

| Boundary | Required control and negative cases |
| --- | --- |
| Authority | A correctly bound synthetic invocation reaches an isolated peer. No permit, invalid signature, wrong purpose/key, fixture authority on the production path, tampered envelope, or mixed candidate/plan/checker gets as far as attachment. Production constructors cannot accept a test-only trust root. |
| Single use | Race two claims of one permit, drop before claim, cancel after claim, attempt reuse after success or crash, fork or restart and present the old bytes. Only one authorized invocation may make a first side effect. An ordinary installed invocation has no generic session, approval or means to manufacture a permit. |
| Budgets and failure | Test zero, exact limit and one over for each allowed operation class, bytes and token allowance. Exercise cutoff before send, drop during send, response after cancellation, partial response, unknown delivery, exhausted re-verification budget and changed peer. Account for both verification probes. No double debit, refund or implicit replay. |
| Content and custody | Compare the real serializer's pre-send body to the verified peer, then validate the full native response and exact untrimmed canary bytes. Exercise extra whitespace, wrong marker, abnormal stop and bad usage. The wrong recursive decoder-schema order fails even if the JSON values compare equal. An evidence receipt cannot be admitted as an enrollment, and a valid enrollment alone cannot satisfy an instance canary. |

In the later offline proof, exercise the release-form build with missing, untrusted and synthetic signatures and show zero attempts at the transport observer. Run the positive case using a separately identified synthetic trust root in an isolated test build. Demonstrate that runtime inputs cannot select that root in the release build. Record the exact identities of both builds and the difference between them.

The challenge costs the operator one local preparation before signing the intended invocation. A reusable signed file can be copied and spent again. Binding it to one pending runner prevents that without a persistent authorization service. The design assumes integrity of the running approved binaries, OS and operator key custody. It does not establish integrity against a workstation owner replacing or instrumenting the verifier. Numeric caps protect a shared workstation and make qualification evidence attributable. Their values belong to the measured candidate annex. Customer eligibility and shipping hardware policy are separate.

## Acceptance and handoff

Connect Runtime owns issuer/admission design, the bounded client entry and the synchronous adapter. The Doc Sum qualification owner must confirm that its r2 preparation and reservation harness can drive the staged G1/G2 transitions and validate final wire order. Its held writer and candidate-specific preflight/quality receipts stay with that owner. Oversight reviews the design, including the synthetic-versus-production boundary. Juan's exact-revision acceptance settles these design semantics only. Implementation, an actual trust anchor, builds, native Windows proof, live numeric annexes and production enrollment remain separate decisions. The immediate proof after an accepted design is the isolated synthetic permit path. It needs no model, tokenizer service or GPU.
